# vatSys Window Manager review (27 Nov 2026)

Reviewed at commit `2051e5b` (v1.1.6), against vatSys **0.4.9305.35667**.

> **Status:** this describes version 1.1.6. The findings were addressed in the 1.2.0 rewrite
> (`src\`). Line numbers below refer to the old single file `WindowManagerPlugin.cs`, which no
> longer exists. For how the current code works see the README and
> [vatsys-internals.md](vatsys-internals.md).

## How this was checked

- Read all of `WindowManagerPlugin.cs` (5,035 lines), the csproj and the README.
- Decompiled the installed `vatSys.exe` with ilspycmd (the OzServer audit method) and checked every
  vatSys member the plugin reflects into against the real code. The decompile is in a scratch folder
  and is not in this repo. This document cites member names and line numbers only.
- Read the eight saved layouts in `Documents\vatSys Window Manager` to see what actually gets saved.
- Compared against the OzServer plugin: `docs/vatsys-internals-audit.md`, `UiThread.cs`,
  `ClosedWindowSweep.cs`, `ArrivalListSync.cs`, the csproj and the build notes.

**Not done:** nothing was run inside vatSys. Every finding is from reading code and saved data.
Findings marked *(by reading)* describe behaviour I traced but did not reproduce.

## Verdict

The plugin restores window positions reasonably well, but it does not yet recall strip setup, ATIS
windows or arrival lists reliably, and it has three behaviours that can affect live controlling.
Most of the retry timers in the code exist to paper over one ordering problem (R1). Fixing that, and
asking vatSys's own registries for windows instead of guessing, removes most of the complexity.

Suggested order is at the end. Each finding has an ID so you can pick by ID or by batch.

## R: recall is wrong or incomplete

### R1. Auto-load on position change is overwritten by vatSys straight afterwards (High)

`MainForm.SetPosition` (MainForm.cs:2281) does three things in order: `MMI.SetPrimePosition`, then
`MMI.LoadPositionStripWindows`, then `ASD.LoadPosition`. The `PrimePositonChanged` event fires inside
the first call. The plugin's handler (`WindowManagerPlugin.cs:119`) goes through `RunOnUiThread`,
which runs the action inline when already on the UI thread (`:156`). So the whole restore runs
before vatSys has finished changing position. vatSys then:

- closes all five state strip windows, deletes every beacon window, opens the position's default
  strip windows, and sets strip mode and sort mode to the position's defaults (MMI.cs:2788);
- resets the main ASD's centre, range, rotation and maps to the position's defaults.

Result: after an auto-load on position change, strip setup is the position default, not the layout.
The ASD mostly recovers only because of the 250/600/1400 ms re-apply timers.

**Fix:** always post the restore (`BeginInvoke`) from the position-changed handler so it runs after
`SetPosition` returns. Most of the retry timers can then go (see H3).

### R2. Beacon, ADEP and ADES strip windows cannot be recreated (High)

`CreateStripWindow` (`:2920`) only calls `MMI.OpenStripWindow`. For beacon-type windows that method
only shows a window that already exists in `MMI.BeaconW`; it creates nothing (MMI.cs:2986). The
method that creates one is `MMI.CreateBeaconStripWindow(type, beacon, index)` (MMI.cs:2868), which
the plugin never calls.

Your three Melbourne TCU layouts each hold four ADEP windows (YMML, YMAV, YMMB, YMEN). They only come
back if the position's own defaults happen to define the same four.

Also missing from the save: beacon windows that are defined but hidden, their order (vatSys names
them `beacon0StripWindow`, `beacon1…` by index, and Strip Setup shows them in that order), and the
Other window's position when it is hidden. Extra beacon windows are hidden on restore but never
removed from Strip Setup (`CloseExtraStripWindows`, `:1595`).

**Fix:** save the full strip model: mode, sort mode, visibility of the five state windows, the
ordered beacon list (type, point, visible, placement), and the Other window's placement. Restore by
deleting beacon windows not in the layout, creating missing ones with `CreateBeaconStripWindow` in
order, then showing or hiding each.

### R3. When a strip window is not found, another one is taken over or a fake one is made (High, by reading)

- `FindExisting` falls back to "same type and same form name" (`:1803`). Beacon windows are named by
  index, so `beacon0StripWindow` matches whatever beacon window is currently first.
- `FindBroadExisting` falls back to the first unused window of the same type (`:1862`), which for a
  strip entry can be any strip window, including the hidden Other window.
- `ApplyStripState` (`:3880`) then writes the saved state into the window's `State` field.
  `StripWindow.WindowType`, `State` and `Beacon` are `readonly` and set by the constructor
  (StripWindow.cs:25-29). `MMI.ShouldStripBeAdded` reads `State`, so writing it on the wrong window
  makes that window show the wrong strips for the rest of the session.
- `TryCreateWithFallback` (`:2339`) will construct a `StripWindow` directly. A window made that way
  is not in `MMI.BeaconW`, so vatSys never sends it strips. It looks right and stays empty.

**Fix:** delete `ApplyStripState`, the type-only and name-only matches for strip windows, and the
generic constructor fallback (see S4). Match strip windows only on type + state + beacon.

### R4. ATIS windows: blank ones are created, missing ones are never opened (High, confirmed in saved data)

`RestoreAtisWindow` only reuses an existing window ("Don't create new ATIS windows", `:1946`). When
it finds none, `CreateWindow` falls through to `Activator.CreateInstance` (`:2558`), which makes a
blank `ATISWindow` with no callsign. Both Sydney TCU layouts contain two such windows (name
`ATISWindow`, title `ATIS`, no callsign). Once saved they are recreated on every load.

`MMI.OpenATISWindow(callsign)` is public and is what vatSys itself uses (MMI.cs:3150, limit of 5).

ATIS windows are also matched by form name `atis0Window`, `atis1Window`, which is an index, so a
different airport's ATIS window in the same slot is treated as the right one (`:2472`).

**Fix:** save the list of ATIS callsigns. On restore close the ones not wanted, call
`MMI.OpenATISWindow` for the missing ones, then place each by callsign. Drop saved entries with no
callsign when loading old layouts.

### R5. ATC list position (the v1.1.6 feature) never saves anything (Medium, confirmed)

The capture reads `X`, `Y`, `Width`, `Height` with `GetField` (`:1059-1066`). On
`SharpDX.RectangleF` (4.2.0) those are properties. The fields are `Left`, `Top`, `Right`, `Bottom`.
Every read returns nothing, the width/height check fails, and no keys are written. None of your
layouts contain an `AtcList…` key, including the one saved in September.

**Fix:** read and write `Left/Top/Right/Bottom`. Do the same for `scaleRectangle` (the scale marker),
which is stored the same way and is not saved at all.

### R6. Arrival lists: far more machinery than needed, and it runs off the UI thread (Medium)

`MMI.OpenArrivalListWindow(airport)` is public and synchronous, and `MMI.ArrivalLists` is the list of
open ones. The plugin instead pre-fires the menu, opens each list twice, polls from a worker thread,
and schedules six clean-up passes over 12 seconds (`:1202-1302`).

- `EnsureArrivalWindows` runs on `Task.Run` and calls `FinalizeRestoredWindow` there, so window
  moves, title changes and `Show()` happen off the UI thread.
- `TrySimulateArrivalMenu` (`:1373`) opens the Windows menu, the Arrival List submenu and the Open New
  submenu with `ShowDropDown` and never closes them. The handler it then invokes does nothing more
  than call `MMI.OpenArrivalListWindow`, which was already called one line earlier.
- With OzServer on, see H6: the window being waited for is replaced by OzServer's.

**Fix:** save the airport list. Restore on the UI thread with `MMI.CloseArrivalListWindows` plus one
`MMI.OpenArrivalListWindow` per airport, then place each by airport.

### R7. ASD: side effects and a restore that fights itself (Medium)

- `SetAsdCentre` calls `SetDisplayCenter(coord, true, true)` (`:3674`). The third argument moves the
  network visibility centre when auto vis centres are on. vatSys's own `LoadPosition` passes `false`.
- The plugin overwrites `StoredCentreLL` and `StoredRange` (`:3552`, `:3662`). Those are the
  controller's own Store/Restore/Recenter view (ASDControlDX.cs:2983-3014), not scratch fields. The
  real stored view is not saved either.
- `ReapplyAsdView` calls `LoadPosition` a second time 200 ms later (`:1974`), which resets centre,
  range and maps again before they are re-applied. It works, but the display jumps, and panning in
  the first 1.5 s after a load snaps back.
- `ApplyRangeToControl` and `AttachRangeRestoreOnChange` (`:3578`, `:3697`) are a fallback for when
  `SetZoom` is missing. It exists, so they never run. If they did they would set the `range` field
  without changing the zoom, and one of the methods they look for (`OnRangeChanged`) does not exist.
- The position is applied by calling `LoadPosition` directly, so the window's Position menu tick and
  title are not updated. The plugin then writes its own title (see S6).
- The saved `DisplayPositionCallsign` and `DisplayPositionFullName` are never written:
  `LogicalPositions.Position` has no such fields.

**Fix:** set position by clicking the window's own Position menu item (matched by its tag), then
centre with `setVisCenter: false`, then `SetZoom`, then maps, once, after the window has drawn.
Save the stored view as its own item. Delete the fallback.

### R8. Window state is not exact (Medium)

- **Minimised windows** *(by reading)*: the saved "actual" rectangle of a minimised window is
  (-32000, -32000). On restore the window is un-minimised and then moved to that rectangle
  (`ApplyPlacement`, `:4040`), which puts it off-screen.
- **Hidden vs shown**: VSCS, ATIS and arrival windows are saved even when hidden, and every restored
  window is shown and brought to front (`:1748`). Hidden-at-save becomes visible-at-load.
- **Z-order** is not saved. Windows come back in enumeration order, each brought to front in turn.
- **Monitors**: no check that a saved rectangle is still on a connected screen. vatSys has a public
  `MMI.EnsureWindowVisible(Form)`.
- `EnsureZOrder` (`:4235`) sets the owner and toggles `TopMost` on every activate and deactivate, for
  the life of the window. vatSys already owns its windows to the main form.

**Fix:** save visible, window state (normal / minimised / maximised), normal rectangle and z-order
per window. Never use the actual rectangle for a minimised window. Remove the `TopMost` handlers.

### R9. Chat and other single-instance windows (Low to Medium)

- Private message windows are saved by recipient, so every later load reopens a chat to whoever you
  were talking to when you saved (`:969`, `:2520`).
- System Messages and ATC Messages are `MMI.SystemMessagesWindow` and `MMI.ATCMessagesWindow`. The
  plugin saves their type but cannot reopen them, and can construct an unregistered copy instead.
- Strip Setup, Sectors and similar are single instances held on `MMI`. The plugin makes a second
  copy with `Activator.CreateInstance` (`:2558`). vatSys's menu then opens its own, giving two.

**Fix:** do not save private message windows. Open single-instance windows through their `MMI`
field, as vatSys's own menu handlers do.

## S: side effects on live controlling

### S1. Loading a layout rewrites your controlled sectors (High)

`ApplyControlledSectors` (`:4356`) calls `MMI.SetControlledSectors` with the saved list on every
load, connected or not. vatSys hands off to nobody every aircraft you are tracking in any sector
that is no longer in the list (MMI.cs:1255). The guard is only `sectors == null`, so a layout saved
with no sectors releases all of them. vatSys itself only sets sectors from a position when you are
not connected (MMI.cs:1022). With OzServer, sector ownership is the server's to decide.

**Fix:** only apply saved sectors when not connected, never apply an empty list, and make it a
per-layout option that is off by default.

### S2. A position change closes windows the plugin does not own (High)

`CloseNonDefaultOnPositionChange` (`:3396`) runs on every position change, whether or not the new
position has an auto-load layout. It closes every window except the main form and VSCS. That
includes the ATIS and arrival windows vatSys has just opened for the new position, and any other
plugin's windows. Closing another plugin's form disposes it; a plugin that keeps one instance can
then fail when it next shows it.

The loop also enumerates `Application.OpenForms` while closing forms, so it stops at the first window
that really closes *(by reading)*. What gets closed therefore varies.

`CloseWindowsNotInSnapshot` (`:2450`) does the same to other plugins' windows on a manual load.

**Fix:** do nothing on a position change unless a layout will load. Only ever close windows of
types the plugin manages. Leave other plugins' windows alone unless they are in the layout.

### S3. Clicking menu items by loose text match (Medium, by reading)

When a saved window's type cannot be found (for example its plugin was removed), `CreateWindow`
clicks the first main-menu item whose text *contains* the window title, the title's first word, the
form name, the type name, or the literal `VSCS`, which is always added (`:2575-2630`, `:2741`). It
sleeps the UI thread for up to 1.2 s per attempt.

**Fix:** remove. Keep only explicit, exact openers for known windows.

### S4. Constructing vatSys windows directly (Medium)

`Activator.CreateInstance` (`:2558`) and `TryCreateWithFallback` (`:2339`, which picks the shortest
constructor and invents arguments) create windows vatSys does not know about. This is the cause of
R4 and part of R3 and R9. The OzServer audit found that every window ever created stays referenced
for the life of the process, so these also add to memory use.

**Fix:** replace both with a small table of openers, one per supported window type. Only second ASD
and Ground windows are meant to be constructed directly (vatSys does `new ASDWindow().Show(main)`).

### S5. Blocking the UI thread (Medium)

`Thread.Sleep` on the UI thread: 12 × 150 ms waiting for OzStrips (`:2593`), 6 × 200 ms per menu
candidate (`:2616`). A window created on the UI thread cannot appear while that thread sleeps, so
these waits cannot succeed. `Application.DoEvents()` (`:2873`) allows re-entry mid-restore.

### S6. The main window title is replaced (Low)

`UpdateWindowTitleFromMetadata` (`:1987`) sets the main form's title to the position name, replacing
`vatSys [Beta][build …]`. Saved layouts show the title already changed to `Sydney TCU`.

## H: hardening, from what OzServer taught us

### H1. One guarded way onto the UI thread (High)

OzServer's `UiThread.Guard` exists because vatSys runs with `UnhandledExceptionMode.ThrowException`:
an exception escaping a posted delegate or an event handler ends the process. Here `RunOnUiThread`
posts bare actions, picks the first open form as its target (at startup that is the Errors window,
not the main form), and runs inline on the calling thread when there is no form. Most paths have
their own try/catch; it is not systematic. `Application.OpenForms` and `form.Handle` are also read
from worker threads (`:4110`, `:4169`).

**Fix:** one dispatcher that always targets `MMI.MainForm`, always posts, and wraps the action.

### H2. Ask vatSys for its windows instead of scanning `Application.OpenForms` (High)

The code has already found that ATIS, arrival and VSCS windows are not always in `OpenForms` and
patches each case. Windows shown through `BaseForm.ShowWithPlacement` are shown natively and can be
missing from it. vatSys keeps exact registries: the five state strip windows and Other as fields,
`MMI.BeaconW`, `MMI.ATISWindows`, `MMI.ArrivalLists`, `MMI.PrivateMessageWindows`, `MMI.VSCSWindow`
and the named single-instance fields. For everything else, enumerate the UI thread's top-level
windows natively.

This also removes the need for `ShouldAlwaysSave`, the `IsMainVatSysForm` first-form fallback
(`:4296`, which currently treats the Errors window as the main form), and title-based matching.

### H3. Replace the timers with one "apply when ready" queue (Medium)

There are 12 `Task.Run` calls and roughly 40 scheduled re-applies per load (arrival clean-ups,
OzStrips placement at 7 delays × 5 retries, ASD centre/range/maps). After R1 most are unnecessary.
For windows that genuinely appear late (OzStrips), keep a short list of pending placements and check
it on `Application.Idle`, which is what OzServer does for its menu items. Apply once, then drop it,
so a user who moves a window is not overridden.

### H4. No diagnostics in a release build (High)

All 48 log lines are `Debug.WriteLine`, which is compiled out of Release. The arrival log is
stubbed. There are about 80 empty `catch` blocks. When a restore goes wrong on someone's machine
there is nothing to look at.

**Fix:** a log file in the layout folder, and a short result after each load ("could not restore:
ADEP YMEN strip window, point not defined") raised through vatSys's Errors window.

### H5. Resolve vatSys internals once, and check them at start-up (Medium)

Reflection lookups are scattered and repeated on every call. Several look up things that are
public and need no reflection: `MMI.PrimePositonChanged` (hooked by writing the event's backing
field, `:116`), `MMI.SectorsControlled`, `MMI.StripMode`, `MMI.StripSortMode`,
`MMI.SetControlledSectors`, `MMI.OpenATISWindow`, `MMI.EnsureWindowVisible`.

**Fix:** one class that resolves every non-public member at start-up, logs what is missing, and
turns off only the feature that depends on it. Keep the list in `docs/` as OzServer does, so it can
be rechecked after a vatSys update. Status today is in the appendix.

### H6. Arrival lists when OzServer is running (Medium)

OzServer closes each vatSys arrival list as it appears and opens its own in the same place
(`OzServerPlugin.ArrivalListWindow`, named `OzServerArrivalList{airport}Window`, public `Airport`).
The plugin only recognises type names ending `SequenceWindow`, so:

- on save, OzServer's list is stored as an unknown window with no airport;
- on restore it cannot be reopened, and for old layouts the plugin waits for a vatSys window that
  OzServer is about to replace.

**Fix:** treat "arrival list for airport X" as the saved item. Open it with
`MMI.OpenArrivalListWindow`, then on the next idle find whichever window now shows that airport
(either type has an `Airport` property) and place it.

### H7. Reuse windows instead of closing and reopening (Low)

Each restore starts by closing every window the plugin opened before (`ClosePluginWindows`, `:810`,
`:830`) and then reopens them. OzServer's `ClosedWindowSweep` documents that vatSys never releases a
closed window (about 470 KB each). Reconfigure existing ASD and Ground windows where the type
matches.

## Suggested order

1. **Batch 1, recall:** R1, R2, R3, R4, R5, with H2 for strips and ATIS. This is the strip and
   Beacon recall you asked for, and it removes the blank ATIS windows.
2. **Batch 2, safety:** S1, S2, S3, S4, S6, R7's visibility-centre and stored-view fixes.
3. **Batch 3, hardening:** H1, H3, H4, H5, H6, R6, R8, R9.
4. **Batch 4, housekeeping:** C1 to C9, H7.

Batches 1 and 2 touch the same restore code, so doing them together is less work than doing them
apart. Batch 4's file split (C1) is easier before Batch 3 than after.

Each batch needs a check in your vatSys afterwards. I cannot verify window behaviour from a build
alone.
